제가 일하는 방식

화면은 최신값만 지연 없이 필요해서 Pub/Sub을, 알람 평가·이력 적재는 값이 유실되면 안 되기 때문에 Stream을 씁니다. deliveryReliability 값(realtime / durable / both)으로 구독마다 채널을 선택하게 해서, 소비자 특성에 안 맞는 채널을 강제하지 않도록 했습니다.
500ms는 트랜잭션 수 대비 화면 체감 개선이 미미했고, 5초는 운영자가 느리다고 느끼는 지연이었습니다. 가장 느린 프로토콜(BACnet)의 폴링 사이클을 온전히 담는 최소 단위가 1.5초였고, 실측 p99 이벤트 루프 지연(38.6ms)에도 여유가 남는 값이었습니다.
구독 설정 변경 빈도가 데이터 유입 빈도보다 압도적으로 낮아서, 최대 30초 지연은 감내할 수 있다고 판단했습니다. 캐시 갱신 자체가 실패하면 예외만 로깅하고 기존 캐시를 그대로 유지해, 파이프라인 전체가 멈추지 않도록 했습니다.
서버가 받은 순서를 신뢰하지 않고, 디바이스가 값을 측정한 시각을 기준으로 최신값을 판정합니다. 화면용 미러 테이블은 최신값 덮어쓰기로 충분하다고 보고 별도 순서 보장 장치를 두지 않았고, 원본 이력은 전량 적재해 필요하면 타임스탬프로 재정렬할 수 있습니다.
장애 격리(한 서비스의 쓰기 부하가 다른 서비스 커넥션 풀에 영향을 주지 않아야 함)와 배포 독립성(서비스마다 마이그레이션 시점이 다름) 때문입니다. 스키마만 나누면 커넥션 풀과 락 경쟁은 여전히 공유되어 리소스 격리가 되지 않습니다.
순찰은 회차·구역별로 담당자 1인이 배정되는 운영 구조라 동시 수정 자체가 발생하지 않도록 이미 배제돼 있었습니다. 그래서 복잡한 병합 로직 대신, 작성 시각 기준 업로드와 회차·포인트 단위 고유 키로 중복만 막는 단순한 규칙을 선택했습니다.
Claude API 키가 없거나 레이트리밋·네트워크 오류가 나면 무조건 통과(relevant=true) 처리하는 fail-open 설계입니다. AI는 "노이즈를 줄이는 2차 필터"일 뿐이고, 알림 서비스의 본질은 "매칭된 걸 놓치지 않고 전달하는 것"이라 AI 인프라 장애가 알림 전달 자체를 막는 단일 장애점이 되면 안 된다고 판단했습니다.

SI/FMS 리뉴얼

NestJSTypeORMPostgreSQL TimescaleDBRedisNext.js DockerGitHub Actions Modbus·MQTT·OPC-UA·BACnet·SNMP
왜 리뉴얼했나

기존 ASP.NET(Windows Server·MS-SQL) 시스템은 라이선스 비용 부담과 기술적 한계가 있었습니다. 오픈소스 전환으로 비용을 없애고, OS·DB에 비종속적인 구조로 향후 MSA 전환 기반을 확보하며, 더 넓은 개발 생태계로 채용 풀을 넓히는 것이 목표였습니다.

아키텍처

Hexagonal Architecture(NestJS·TypeORM·PostgreSQL·Redis 백엔드, Next.js 프론트엔드)로 설계했고, 인증 서버·SI 백엔드·FMS 백엔드·SI 커넥터 등 10개 이상 서비스를 Docker Compose 기반으로 구성·운영합니다. GitHub Actions CI/CD와 현장별 선언적 배포(이미지 버전 고정, 오프라인 번들, 드리프트 추적)를 함께 구축했습니다.

핵심 모듈 5가지
  • 실시간 데이터 파이프라인: Modbus·MQTT·OPC-UA·BACnet·SNMP 기반 디바이스 3,501대·태그 3만 개 규모를 Redis Pub/Sub(실시간)·Stream(무손실) 이중 채널로 배포, 초당 9,000건(시간당 약 3,200만 건) 처리 용량 검증
  • 인증·인가 체계: JWT 발급 전담 서버 분리, axios 인터셉터 single-flight로 동시 401을 1회 갱신으로 병합, WebCrypto 기반 AES-256-GCM으로 브라우저 로컬 저장값을 암호화(미지원 환경 대비 폴백 포맷 포함)
  • TimescaleDB 대용량 운영: 이력·알람·제어로그 하이퍼테이블 전환, 누적 27.8억 건을 365일 보존·3개월 압축 정책으로 653GB → 35GB(94.6% 절감)
  • 순찰관리 오프라인 동기화: 통신이 불안정한 지하·기계실 대응, Flutter 앱에 API 클라이언트 → 리포지토리 → 로컬 DB → 동기화 매니저로 이어지는 오프라인 우선 구조를 구현하고, 서버 재동기화 시 충돌 레코드를 일괄 덮어쓰기 대신 건별로 선택해 반영하는 충돌 해결 화면까지 설계
  • 실시간관제(SI) 프론트엔드 엔진: 노드 그래프 기반 가상 태그 수식 인터프리터(순환참조 실행 중 탐지, 저장 전 구조 검증)를 직접 설계·구현했고, 초 단위로 값이 갱신되는 대시보드는 requestAnimationFrame 배치 플러시와 화면별 파티셔닝으로, 도형 수백 개 규모의 캔버스 HMI 에디터는 도형 타입별 커스텀 리렌더 비교자로 성능을 확보
  • 실시간 알람(SSE) 성능 최적화
    문제 서로 다른 목적(캐싱·알람평가)의 두 컨슈머가 같은 텔레메트리를 이중 구독, 매 메시지마다 DB 조회 발생
    해결 구독 메타(30초)·알람규칙 존재여부(5초) 캐싱으로 불필요한 DB 접근 차단
    결과 초당 수백 건 유입 시에도 커넥션 풀 고갈 없이 안정 처리
  • DB 커넥션 풀·타임아웃 정책
    문제 API 서버(동시요청 多)와 폴러(순차처리 위주)가 같은 풀 설정을 써서 특성이 안 맞음
    해결 역할별 풀 사이즈 분리(API 20 / 폴러 10), idle·connection·statement 타임아웃 세분화
    결과 1초 이상 쿼리 자동 로깅 체계까지 확보해 병목을 조기 탐지 가능
  • 선언적 현장 배포 시스템
    문제 폐쇄망이라 원격 배포가 불가능, 현장마다 이미지 버전이 제각각으로 흐트러짐
    해결 site.conf(선언) + USB 오프라인 번들 + state/(회수한 실제 상태) 구조로 표준화
    결과 "선언과 실제의 차이"를 항상 추적 가능, 현장 간 일관성 확보
  • GitHub Actions CI/CD 개선
    문제 배포 파이프라인 실패 시 원인(네트워크·DNS·포트)을 파악하기 어려움
    해결 SSH 연결 진단 스텝 추가, 불안정한 @master 참조를 @v1 고정 버전으로 교체
    결과 배포 실패 원인 진단 시간 단축, 파이프라인 안정성 개선
  • 설비 자동화(UBM) 누적 로직
    문제 분당 1행씩 적재 시 행 수 폭증, 매분·정시 트리거가 겹치며 중복 적재 위험
    해결 15분 버킷 단위 누적 + 처리 시각 기록(lastRuntimeAt) 기반 재처리 차단
    결과 스케줄러 중복 실행에도 데이터 정합성(멱등성) 유지
  • 소켓 재연결과 토큰 갱신 분리
    문제 토큰이 주기적으로 갱신될 때마다 소켓을 끊고 재연결하면 실시간 데이터 수신이 불필요하게 끊기는 구조였음
    해결 최초 연결과 단순 토큰 갱신을 구분해 갱신 시엔 소켓을 유지하고, 인증 만료로 인한 연결 에러일 때만 단일 Promise 기반 리프레시로 재연결하도록 설계
    결과 토큰 갱신 주기마다 발생하던 불필요한 재연결 제거
그 외 설계·구현
  • API 설계: CQRS 스타일로 Command/Query 컨트롤러를 분리해 다수 도메인의 REST API를 설계·구현
  • 팀 전파: 백엔드 설계 컨벤션 수립 및 인수인계서 작성
부가 도구

  • 관리자 API의 N+1 쿼리 (2건)
